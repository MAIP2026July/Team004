# Feature Prioritisation

## 1. Method

Features are prioritised using MoSCoW: Must Have, Should Have, Could Have, and Will Not Have in the initial controlled pilot. The decision considers user value, governance necessity, data readiness, complexity and consequence of failure.

## 2. Prioritised Features

### Must Have

| Feature | Reason |
|---|---|
| Structured risk intake | Foundation for traceable analysis |
| Mandatory-field and date validation | Reliable deterministic baseline |
| Human-approved risk inputs | Prevents autonomous material scoring |
| Inherent and residual calculation | Consistent prioritisation |
| 5 × 5 heatmap and gate rules | Connects score to governance action |
| Evidence-gap review | Challenges unsupported claims |
| Related-risk suggestions | Reduces fragmented review |
| Explanation and limitations panel | Enables informed human review |
| Accept/reject/modify/escalate actions | Preserves human authority |
| Audit trail | Required for accountability |
| Critical-risk blocking | Prevents unsafe progression |

### Should Have

| Feature | Reason |
|---|---|
| Basic drift monitoring | Supports post-deployment assurance |
| Supplier evidence checklist | Addresses third-party opacity |
| Role-based dashboards | Improves decision relevance |
| Residual-risk trend | Shows change over time |
| Exportable governance report | Supports review and audit |

### Could Have

| Feature | Reason for deferral |
|---|---|
| Synthetic edge-case generation | Requires domain validation and compute |
| Portfolio analytics | Needs multiple programmes or sites |
| Automated framework cross-walk | Lower priority than evidence and decisions |
| Advanced supplier benchmarking | Requires comparable supplier data |
| Natural-language executive summary | Useful, but not a core control |

### Will Not Have in Initial Pilot

- Autonomous risk acceptance, closure, launch or commissioning
- Regulatory or safety certification
- Automated operational remediation without approval
- Enterprise-wide deployment before controlled-pilot evidence

## 3. Prioritisation Rules

1. Governance and human-control features outrank convenience features.
2. Deterministic validation precedes contextual AI capability.
3. Critical operational AI remains in shadow mode until validated.
4. A feature without data, owner, test method or failure response cannot enter the pilot.
5. Cross-domain expansion follows proof of repeatability in the primary workflow.

## 4. Release Mapping

| Release | Included focus |
|---|---|
| R0 Prototype | Risk intake, score calculation, heatmap and sample AI observations |
| R1 Controlled MVP | Human workflow, evidence review, related risks, explanations and audit |
| R2 Shadow Pilot | Drift alerts, supplier evidence and domain testing |
| R3 Paid Pilot | Integration, role dashboards, export and value measurement |
| R4 Scale | Portfolio analytics, reusable domain configurations and supplier integration |
